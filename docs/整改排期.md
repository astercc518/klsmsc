# 短信网关整改排期清单

> 依据 2026-07-01 运行满 2 个月的多智能体深度审计（12 子系统，确认 94 条发现：5 Critical / 69 High / 5 Medium / 15 Low）+ 通道路由补审 10 条。
> 本文件是**执行排期**；完整审计结论与证据见审计报告，关键根因见项目记忆 `project_deep_audit_2026_07`。

## 指导原则

- P0 全部"小改动、可回滚、有验收断言"。
- 财务类改动一律**改前向 + 生成对账差异清单交财务**，不擅自追溯改历史金额。
- DB 重活排低峰维护窗口，先在副本演练 + 备份。
- 每批次配"验收断言 + 回滚步骤"再上生产。

## 0. 总览

| 阶段 | 周次 | 主线目标 | 并行轨 |

## 2. 并行轨 · 可观测性最小闭环（第 1 周起，贯穿始终）

可观测性是放大所有隐患的元根因，先落最小版本，用来验证 P0/P1 是否真见效（约 2–3 人日，先 StatsD/日志埋点 + 简单告警即可）：

| 指标 | 告警线 | 用途 |
|---|---|---|
| DLR 重试缓冲大小 / result 缓冲大小 | 缓冲 > 1w | 抓 OOM 前兆 |
| `p_future` / 各分区行数 | p_future > 500w | 分区失效告警 |
| 死锁重试计数 | 突增 | 抓 sms_logs 死锁降级 |
| Go 网关 goroutine 数 / bind 数 | 单调增 | 抓泄漏 |
| worker 崩溃率 / 队列积压深度 | 积压 > 阈值 | 抓丢单/延迟 |

## 3. 第二阶段 · P1 治本（第 3–8 周）

按主题成组，组内可并行，组间大致按下列顺序：

| 组 | 任务要点 | 量 | 关键验收 |
|---|---|---|---|
| **幂等下沉 DB** | webhook/注水/虚拟 DLR 加 DB 唯一约束（`UNIQUE(sms_log_id,action)` 等）；虚拟 DLR 批量入口加分布式锁 | 4–5 人日 | Redis 故障期不再 4 倍重复派发 |
| **路由 R1/R2** | 重发原通道停用时**明确失败/退回私库**不降级；专国绑定全不可用时的回退语义确定 | 2–3 人日 | 重发严格沿用原通道；DLR 不再对不上假成功 |
| **分片资金守恒** | 分片两阶段提交或单条补偿退款；批次取消触发批次级退款；`use_count` 延后到全部入队成功 | 5–6 人日 | 无"扣全额发一半"；取消即退款；库存不漂移 |
| **缓存架构** | price/route 禁 L1；L1 加 TTL+上限；`delete_pattern` 改 `scan_iter`；定价/私库加 SETNX 单飞+负缓存 | 3–4 人日 | 改价即时生效；整点无雪崩；进程不 OOM |
| **Go 网关** | 在途计数 per-session 隔离；移除 TPS 桶 cap；结果发布加重试队列；限流恢复用 timer 去重、清 bind 泄漏 | 5–7 人日 | 多路吞吐提升数倍；间歇故障不丢 sent；资源有界 |
| **Celery 吞吐** | 按队列覆盖 prefetch；result 缓冲加 maxsize；`fetch_dlr` 加分布式锁 | 2–3 人日 | 回执延迟 30min→秒级；result worker 不 OOM |
| **DLR 管线韧性** | 孤儿阈值/TTL 对齐；flush 超时立即投下一个；redis 客户端改连接池；删同步 `update_batch_progress` | 3–4 人日 | 大积压期不误丢真实送达 |
| **报表口径统一** | 抽 `_virtual_channel_ids` 公共模块三端统一；数据业务成本改真实字段；时间全 UTC-aware | 3–4 人日 | 三端口径一致可对账；利润不虚高 |

## 5. 需拍板的决策点（影响做法）

1. **佣金已结算部分**：只出差异清单交财务，还是脚本自动冲抵后续佣金？
2. **分区抢救窗口**：能否安排低峰维护窗口（P0-8 重写 p_future 全部数据）？还是要"增量不停服"方案？
3. **专国路由回退（R2）**：专国通道全停用时，回退全国默认兜底发出，还是明确拦截要人工介入？
4. **重发原通道停用（R1）**：选"失败挂起等人工"还是"退回私库按原通道补发"？
5. **数据业务成本**：短期按真实采购价补建 `cost_price`，还是先置 NULL + UI 标"成本待建账"？

## 6. 通用上线纪律

- worker 改码必 `restart`（volume 挂载不热更）；前端用 `up -d` 非 restart；Go 网关改动需 rebuild。
- Schema 变更只走 Alembic，禁 `create_all`。
- 财务类改动先在对账断言（P0-10）绿灯环境下灰度。
- 每批次配"验收断言 + 回滚步骤"再上生产。

## 附：系统性根因主题（比单个 bug 更值得治理）

1. 幂等押在易失 Redis 且 fail-open → 核心幂等下沉 DB 唯一约束。
2. "最后写入生效"状态机缺终态保护 → 引入 `status_finalized_at` + 合法转移图。
3. 资金守恒不成立（扣费/退款/佣金/use_count 并发脱钩）→ 两阶段提交 + 对账补偿闭环。
4. 时区不一致（naive datetime 混用）→ 全链路 UTC-aware 存储 + 展示层转换。
5. 表/缓冲无界增长无生命周期 → 统一加 TTL/上限/清理。
6. 口径/配置多副本不同源 → 收敛到单一数据源函数。
7. 可观测性近空白 → 元根因，优先补齐。
8. Go 网关并发单位错配（窗口/限速/bind 计数粒度错）。

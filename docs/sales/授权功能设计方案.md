# 授权（License）功能设计方案

> 目标：用同一套授权机制覆盖三种购买方式，做到**离线可验证、难破解、对正常客户无感、对欠费/到期/盗用可控降级**。

---

## 一、三种购买方式对应的授权策略

| 购买方式 | 授权类型 | 绑定 | 到期 | 失效后行为 |
|---|---|---|---|---|
| ① 源码出售 | `edition=source` | 不绑定（或绑定但密钥随源码交付） | 永久 | 不限制（源码自主） |
| ② 部署+永久授权 | `edition=perpetual` | 服务器指纹 + 域名 | 永久 | 校验失败→只读/停发 |
| ③ 部署+1年授权 | `edition=subscription` | 服务器指纹 + 域名 | 1 年（`expires_at`） | 到期→宽限期→停发 |

**关键点**：三种方式共用同一份 License 校验代码，**差异完全由 License 文件里的字段决定**，不需要为每种方式改代码、出不同版本。源码客户拿到的就是一张「永久 + 不绑定」的 License。

---

## 二、技术原理（离线非对称签名）

采用 **Ed25519 非对称签名**，而非简单序列号：

```
[卖方持有] 私钥 (private key)  ——只在你手里，用来签发 License
[随系统交付] 公钥 (public key) ——编译/打包进代码，只能验签不能伪造
```

流程：
1. 你（卖方）用**命令行工具**根据客户信息生成 License：填写客户名、版本类型、到期时间、绑定的服务器指纹/域名 → 用私钥签名 → 输出 `license.lic` 文件。
2. 客户把 `license.lic` 放到部署目录，系统启动时用内置公钥**离线验签**。
3. 客户无法伪造或篡改（没有私钥），改任何一个字段签名都会失效。

> 优点：**无需联网授权服务器**（适合客户内网/海外服务器），同时安全性远高于自定义序列号。可选叠加「在线心跳」用于远程吊销（见第六节）。

---

## 三、License 文件结构

`license.lic` = Base64( JSON 载荷 ) + "." + Base64( 签名 )，类似 JWT 结构：

```json
{
  "license_id": "LIC-20260529-0001",
  "customer": "某某科技有限公司",
  "edition": "subscription",          // source | perpetual | subscription
  "issued_at": "2026-05-29",
  "expires_at": "2027-05-29",          // perpetual/source 为 null
  "bind": {
    "machine_fingerprint": "a1b2c3...",// 服务器硬件指纹，可为 null=不绑定
    "domains": ["sms.client.com"]      // 允许的访问域名，可为空
  },
  "limits": {                          // 可选：额度限制（卖点/防滥用）
    "max_accounts": 0,                 // 0 = 不限
    "max_channels": 0,
    "daily_send_limit": 0
  },
  "grace_days": 7                      // 到期后宽限天数
}
```

**服务器指纹**：取机器稳定标识的哈希，建议组合 `机器 machine-id + 主网卡 MAC + CPU 信息`，做 SHA-256。容器部署时可改用「挂载的宿主机 machine-id + 授权时指定的域名」避免容器重建导致指纹漂移。

## 四、在系统里的集成点（贴合现有架构）

### 1. 新增 `backend/app/core/license.py`
负责：读取 `license.lic` → 验签 → 校验到期/指纹/域名 → 返回 License 对象，结果缓存进 Redis（`license:status`，TTL 1h）。

```python
# 伪代码骨架
class LicenseStatus:
    valid: bool
    edition: str
    expires_at: date | None
    reason: str | None       # 失效原因
    in_grace: bool           # 是否处于宽限期

def load_and_verify() -> LicenseStatus: ...
def require_active() -> None:  # 失效则抛异常/降级
```

### 2. 启动时校验（`main.py` 的 `lifespan`）
- 应用启动时跑一次 `load_and_verify()`，结果写日志 + Redis。
- **失效不直接 crash**（避免客户彻底打不开后台无法续费），而是进入「受限模式」。

### 3. 定时复检（Celery beat）
- 每天/每小时跑一次复检任务，到期自动切换状态，写入 Redis。

### 4. 发送链路拦截（核心约束点）
- 在 `send_sms_task` / `batch_worker` / 发送 API 入口处调用 `require_active()`。
- 这是**最该卡的地方**：授权失效 → **拒绝发送**（但后台、报表、充值仍可访问，方便客户看到提醒并续费）。

### 5. 前端提醒
- 后台顶部 Banner：「授权将于 X 天后到期 / 已到期，请联系续费」。
- 新增只读接口 `GET /api/v1/admin/license/status` 给前端读取状态。

## 五、失效后的分级降级（重要：别一刀切）

| 状态 | 后台登录 | 查看报表/账单 | 充值 | **发送短信** |
|---|---|---|---|---|
| 正常 | ✅ | ✅ | ✅ | ✅ |
| 即将到期（提醒） | ✅ | ✅ | ✅ | ✅（顶部告警） |
| 已到期·宽限期内 | ✅ | ✅ | ✅ | ✅（强提醒） |
| 已到期·超宽限 | ✅ | ✅ | ✅ | ❌ **停发** |
| 指纹/域名不符（疑似盗用） | ✅ | ✅ | ❌ | ❌ **停发** |

> 设计哲学：**只卡发送（你的核心收入命脉），不卡后台**。让客户始终能登录看到「请续费」并完成付款，体验和回款都更好。

## 六、可选增强（按需）

1. **在线心跳吊销**：客户系统每天向你的授权服务器上报一次 `license_id + 指纹`，你可远程标记吊销（应对盗用/纠纷）。无网络时回落到离线宽限，不影响海外/内网客户。
2. **额度型卖点**：用 `limits` 做「基础版 50 通道 / 旗舰版不限」的版本差异化，二次销售扩容。
3. **防篡改加固**：核心校验逻辑可用 Cython 编译为 `.so`，源码出售客户除外。
4. **离线续费**：方案③到期，你重新签发一张新 `expires_at` 的 `license.lic` 发给客户替换即可，**无需重新部署**。

---

## 七、卖方工具（你自己用）

新增一个独立脚本 `tools/gen_license.py`（不随交付给②③客户）：

```bash
python tools/gen_license.py \
  --customer "某某科技" \
  --edition subscription \
  --expires 2027-05-29 \
  --fingerprint a1b2c3... \
  --domains sms.client.com \
  --out license.lic
```

配套 `tools/get_fingerprint.py` 给客户在目标服务器上跑，回传指纹给你签发。

## 八、落地步骤建议

1. 先实现 `core/license.py` + 公私钥生成 + `gen_license.py`（半天）。
2. 接入 `lifespan` 启动校验 + 发送链路 `require_active()`（半天）。
3. 前端 Banner + status 接口（半天）。
4. 三种 edition 各签一张测试 License 跑通验收。
5.（可选）在线心跳 / Cython 加固 后续迭代。

> 说明：方案①（源码出售）建议仍保留授权框架，但交付一张 `source` 永久不绑定 License，并在合同里约束转售——既不影响客户使用，又为后续纠纷留证据链。
